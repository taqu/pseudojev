# Task: Implement R1 — Retrieved 1-Shot Inference Evaluation

## 1. Objective

Implement R1, the first retrieval-augmented inference experiment for pjev.

R1 compares the existing S1 zero-shot inference baseline against an otherwise identical inference pass augmented with the single nearest training exemplar retrieved from the existing SQLite vector database.

The retrieval database is:

`models/exsamplar.db`

The embedding model is:

`models/nomic-embed-text-v1.5.gguf`

The primary objective is to determine whether a semantically retrieved, task-compatible 1-shot demonstration improves Open Jev prediction accuracy.

**R1 is an always-1-shot experiment. Do not implement adaptive gating, similarity thresholds, or multiple demonstrations.**

R1 must measure both improvements and regressions relative to S1.

This experiment must preserve the existing pjev inference semantics and avoid unnecessary modifications to the production inference pipeline.

---

## 2. Experimental design

Evaluate two inference conditions on exactly the same examples.

### S1 — Zero-shot baseline

Run the existing S1 implementation without retrieval or demonstrations.

Preserve:

- Existing inference model
- Existing system instructions
- Existing user prompt formatting
- Existing answer-label mapping
- Existing logit-based decision mechanism
- Existing inference parameters
- Existing probability and margin calculations

Do not reimplement S1 independently if it can be called through the current inference infrastructure.

### R1 — Retrieved 1-shot

For each evaluation example:

1. Generate the canonical query embedding.
2. Retrieve the closest eligible training exemplar.
3. Reconstruct the exemplar from the database.
4. Build a 1-shot prompt containing the exemplar and its correct answer.
5. Append the current evaluation question using the existing S1 task format.
6. Run the same inference model.
7. Extract the prediction using the same answer-label/logit mechanism as S1.

The only intended inference difference between S1 and R1 is the addition of one retrieved demonstration and the minimal formatting needed to distinguish the example from the current question.

Do not change model weights, inference temperature, sampling strategy, or answer decoding.

### Evaluation flow

```text
                 Validation example
                         |
                +--------+--------+
                |                 |
                v                 v
           S1 zero-shot      Query embedding
                |                 |
                |                 v
                |          sqlite-vec Top-1
                |                 |
                |                 v
                |          Retrieve exemplar
                |                 |
                |                 v
                |          Reconstruct prompt
                |                 |
                |                 v
                |          R1 1-shot inference
                |                 |
                v                 v
           S1 prediction    R1 prediction
                |                 |
                +--------+--------+
                         |
                         v
                 Paired comparison
                         |
              +----------+----------+
              |                     |
              v                     v
          Rescue/Harm          Accuracy/Latency
```

## 5. Supported task kinds

Support:

- `choice`
- `noul`
- `score`

The Open Jev dataset uses `kind`, while the pjev API uses `type`.

They refer to the same task discriminator.

Use the existing internal task representation.

### Mandatory retrieval constraints

The retrieved exemplar must have the same kind as the query.

For `score`, it must also have the same number of score levels.

Examples:

```text
choice query
  -> choice exemplar

noul query
  -> noul exemplar

score query, 5 levels
  -> score exemplar, 5 levels
```

Do not mix kinds inside one-shot demonstrations.

For score, preserve the actual score values, score meanings, and answer ordering.

If the task supports different score semantics with identical level counts, record that distinction for diagnostics.

Do not assume that equal level counts imply semantically identical options.

## 6. Retrieval implementation

Reuse the existing R0 retrieval implementation.

Do not implement an independent nearest-neighbor search.

Use:

- The existing Nomic embedding model
- The existing canonical text formatter
- The correct `search_query:` prefix
- The existing normalization policy
- The existing sqlite-vec distance metric
- The existing kind and score-level filters

Load the embedding model once per evaluation run.

Open the exemplar database in read-only mode.

### Top-1 selection

Retrieve the single nearest eligible exemplar.

Use deterministic result ordering.

Do not rerank using the target answer.

Do not select examples based on whether their ground truth matches the query's ground truth.

Do not use the evaluation target during retrieval.

### No similarity gate

Always use Top-1 when at least one eligible exemplar exists.

Do not skip retrieval because cosine similarity is low.

A low similarity is an important R1 diagnostic, not a reason to silently activate an adaptive policy.

If no eligible exemplar exists, record an explicit `no_eligible_exemplar` status.

Do not silently substitute a different task kind.

For overall reporting, distinguish successful 1-shot coverage from unpaired or fallback cases.

Do not treat a zero-shot fallback as an actual 1-shot result.

## 8. Few-shot prompt construction

This is the most important part of R1.

The demonstration must show one complete solved example followed by the current unsolved question.

### Recommended structure

```text
Here is an example of the same task.

Example:
State:
{retrieved_state}

Question:
{retrieved_question}

Possible answers:
A: {retrieved_option_0}
B: {retrieved_option_1}
C: {retrieved_option_2}
...

Answer: {retrieved_correct_letter}

Now answer the new case.

State:
{query_state}

Question:
{query_question}

Possible answers:
A: {query_option_0}
B: {query_option_1}
C: {query_option_2}
...

Answer:
```

This is a conceptual template.

The actual implementation must preserve the existing S1 prompt conventions.

### Preserve S1 format

Do not replace S1's existing state serialization, option rendering, or answer format with an unrelated format.

Prefer composing the demonstration using the same underlying task renderer as S1.

The current query must use exactly the same option ordering and answer-label mapping as it does in S1.

If the existing S1 implementation uses a chat template, preserve that template.

The demonstration and query must be placed in a way that respects the model's actual supported prompt format.

Avoid introducing new system-level instructions unless strictly necessary.

### Answer mapping

A retrieved exemplar may have:

```text
options:
  0: K11
  1: item_82
  2: P72

answer_index:
  1
```

The corresponding demonstration answer must use the same label convention as S1:

```text
A: K11
B: item_82
C: P72

Answer: B
```

Do not output `Answer: item_82` if the model is trained or evaluated to respond using A/B/C labels.

The answer labels must be generated from the retrieved exemplar's own option ordering.

Do not assume the retrieved exemplar and current query have the same number of options.

### Different option counts

For `choice` and `noul`, support the option counts actually accepted by pjev.

For `score`, enforce the existing score-level compatibility rule.

If the existing S1 output head or label-scoring implementation has a maximum supported candidate count, respect it.

Do not silently truncate options.

### Correct answer

Use the stored training exemplar ground truth.

Never use the validation query's ground truth in the prompt.

The validation target must only be accessed during evaluation.

## 9. One-shot prompt safety and integrity

Structured dataset content may contain instruction-like text.

Treat retrieved state and question text as example data, not trusted system instructions.

Preserve the existing task serialization rules.

Do not allow retrieved content to alter runtime model configuration, tool execution, or evaluator behavior.

Ensure that the retrieved answer is clearly associated with its own example, not with the current query.

Do not append explanations or reasoning traces that do not exist in the exemplar data.

R1 is a demonstration-based experiment, not chain-of-thought generation.

## 12. Primary evaluation metrics

R1 must report results overall and separately for each kind.

### Accuracy

Calculate:

- S1 accuracy
- R1 accuracy
- Absolute accuracy difference in percentage points
- Number of correct S1 predictions
- Number of correct R1 predictions
- Total paired examples

Both conditions must be evaluated on the same paired sample.

Do not compare results from different subsets.

### Rescue and harm

These are mandatory.

Define:

**Rescue:** S1 incorrect, R1 correct.

**Harm:** S1 correct, R1 incorrect.

Also track:

- Both correct
- Both incorrect
- Net gain = rescue count - harm count

Use a paired transition table:

| | R1 correct | R1 incorrect |
|---|---:|---:|
| S1 correct | Both correct | Harm |
| S1 incorrect | Rescue | Both incorrect |

Report this table:

- Overall
- By kind
- By score-level count, where applicable

The net accuracy improvement must agree with the rescue/harm counts.

### Paired uncertainty

Where sample size permits, report a paired confidence interval for the accuracy difference.

McNemar's test may be included as a secondary diagnostic.

Do not present an insignificant small gain as conclusive evidence.

Finish with one of these evidence-based recommendations:

### A. Proceed to R2

Retrieved 1-shot provides a measurable benefit or demonstrates a meaningful rescue pattern that could plausibly be improved by similarity gating.

### B. Improve exemplar selection or prompt construction

Retrieval produces semantically relevant examples but demonstrations frequently mislead the inference model.

### C. Do not proceed with retrieval augmentation yet

The retrieved demonstrations cause substantial regressions, introduce unacceptable overhead, or fail to demonstrate a useful rescue pattern.

A positive average accuracy difference is not the only interesting result.

A near-zero average difference with both substantial rescues and substantial harms may still justify investigating selective activation later.

Conversely, a small gain with excessive latency or unstable behavior should not automatically be treated as success.

## Final instruction

The objective of R1 is to isolate the effect of adding exactly one semantically retrieved training example to the existing S1 inference procedure.

Do not combine retrieval experiments with unrelated inference changes.

Preserve the original S1 behavior, evaluate the same questions, and measure both gains and regressions.

**The most important R1 outputs are paired accuracy, rescue count, harm count, and the relationship between retrieval similarity and inference outcome.**
