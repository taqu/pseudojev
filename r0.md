# Task: Implement R0 — Semantic Retrieval Sanity Evaluation

## 1. Objective

Implement R0, a retrieval-only evaluation tool for the existing Open Jev exemplar database.

The exemplar database has already been generated:

`models/exsamplar.db`

Use the path exactly as written. Do not rename, recreate, or rebuild this database.

The objective is to determine whether the existing Nomic embedding representation and sqlite-vec retrieval pipeline return useful, semantically similar training examples for unseen Open Jev questions.

This is a prerequisite for R1 (Retrieved 1-Shot).

**R0 must not run the main pjev inference model, generate few-shot prompts for inference, or modify the existing inference pipeline.**

R0 is strictly a retrieval-quality diagnostic.

## 2. Inspect the existing implementation

Before writing code, inspect:

- The existing `tools/pjevfilldb` implementation
- The actual SQLite schema in `models/exsamplar.db`
- The embedding text formatter
- The embedding model loader
- The existing sqlite-vec integration
- Open Jev dataset organization
- The existing C++ build system and testing conventions

Reuse existing components wherever possible.

Do not assume the database schema is identical to an earlier design proposal.

Inspect the actual schema with SQLite and adapt the implementation accordingly.

Do not introduce a second embedding implementation with different normalization, pooling, tokenization, or text formatting behavior.

The R0 query embedding must be compatible with the stored exemplar embeddings.

## 3. Evaluation input

Use held-out Open Jev examples as retrieval queries.

Preferred input:

`datasets/validation.jsol`

Verify the actual dataset filenames and split organization before implementing the default.

If the repository uses a different validation path, use that path and document the decision.

Do not use training records as the primary evaluation queries.

Do not use test or OOD splits for initial R0 development and threshold exploration.

Do not insert validation records into the exemplar database.

Only the existing training exemplar bank may supply retrieved demonstrations.

Filter evaluation queries to English examples.

## 4. Retrieval constraints

R0 must evaluate the three Open Jev task kinds separately:

- `choice`
- `noul`
- `score`

The dataset field `kind` corresponds to the pjev API field `type`.

### Mandatory filters

All retrieved examples must match the query's kind.

For score tasks, also require the same number of score levels.

Examples:

```text
Query:
  kind = choice

Retrieve:
  kind = choice
```

```text
Query:
  kind = noul

Retrieve:
  kind = noul
```

```text
Query:
  kind = score
  number_of_levels = 5

Retrieve:
  kind = score
  number_of_levels = 5
```

Never mix examples of different kinds in a retrieved few-shot candidate set.

Use the database's native sqlite-vec metadata filtering if available.

Do not run an unrestricted global Top-K and then filter the returned results in application code.

For score, preserve `score_values` and option semantics in the diagnostics.

An equal number of levels does not necessarily imply identical score meanings.

## 5. Query embedding generation

Use:

`models/nomic-embed-text-v1.5.gguf`

Reuse the embedding model integration already implemented for `pjevfilldb`.

The indexed training exemplars should have used:

`search_document:`

The validation query must use:

`search_query:`

Reuse the same canonical embedding text representation, apart from the task-specific prefix.

Requirements:

- Same GGUF model
- Same embedding dimension
- Same tokenizer
- Same pooling behavior
- Same normalization policy
- Same embedding format version
- Same handling of structured JSON
- Same token-length policy

Verify compatibility using the database metadata, if available.

Abort with a clear error on incompatible model or embedding configurations.

Load the embedding model once and reuse it for all validation queries.

Do not include the validation target or correct answer in the query embedding.

## 6. Implement a new R0 tool

Add an independent command-line tool following repository conventions.

Suggested location:

`tools/pjev-r0`

Alternatively, use an existing tooling directory structure if more appropriate.

Suggested CLI:

```bash
tools/pjev-r0 \
  --db models/exsamplar.db \
  --input datasets/validation.jsol \
  --model models/nomic-embed-text-v1.5.gguf \
  --top-k 5 \
  --output results/r0
```

Optional flags:

```text
--limit N
--kind choice|noul|score|all
--top-k N
--exclude-same-group
--verbose
--help
```

The `--exclude-same-group` option should exclude retrieved exemplars sharing the query's group ID.

Do not make this exclusion a silent default. Report group matches in the baseline analysis, then compare with exclusion enabled where relevant.

All output files should be deterministic given identical inputs, database, model, and configuration.

Open the existing database in read-only mode.

## 7. Retrieve Top-K exemplars

For every eligible validation query:

1. Parse the Open Jev record.
2. Extract `kind` and task metadata.
3. Generate canonical query text.
4. Compute the query embedding.
5. Perform sqlite-vec KNN search with the mandatory filters.
6. Return the nearest K eligible training exemplars.
7. Resolve each result to its complete stored example metadata.
8. Record distance, similarity, answer information, and source relationships.

Use cosine distance consistently with the indexed vector table.

If the sqlite-vec distance is cosine distance, report:

`cosine_similarity = 1.0 - cosine_distance`

Do not apply this transformation blindly if the existing vector index uses a different distance metric.

Verify the metric from the database definition.

If fewer than K eligible candidates are available, report the actual result count.

Do not invent or duplicate retrieved results.

For exclusions implemented outside sqlite-vec, ensure enough eligible candidates are searched to produce a true filtered Top-K. Prefer correct SQL-level filtering or an exact eligible-set search rather than fixed-size global overfetch.

## 8. Per-query diagnostic output

Produce a JSONL file:

`results/r0/retrieval.jsonl`

Each record should include:

```json
{
  "query_id": "...",
  "kind": "score",
  "number_of_levels": 5,
  "query_group_id": "...",
  "query_template_id": "...",
  "query_source_instance_id": "...",
  "query_ground_truth": "...",
  "retrieved": [
    {
      "rank": 1,
      "example_id": "...",
      "distance": 0.12,
      "similarity": 0.88,
      "kind": "score",
      "number_of_levels": 5,
      "ground_truth": "...",
      "group_id": "...",
      "same_group": false,
      "same_template": true,
      "same_source_instance": false
    }
  ]
}
```

The example values are illustrative.

Include:

- Query ID
- Query kind
- Query score-level count, when applicable
- Query metadata
- Retrieved example IDs
- Rank
- Cosine distance
- Cosine similarity
- Retrieved ground truth
- Group and template relationships
- Relevant source identifiers

Preserve candidate answer and option ordering information so the result can eventually be used for one-shot reconstruction.

Store diagnostic data separately from the original database.

## 9. Human-readable retrieval inspection

Create a Markdown report:

`results/r0/examples.md`

This report must show representative query/retrieval pairs for manual inspection.

For each selected query, display:

- Query kind
- Query question
- Important state information
- Query answer
- Top-5 retrieved examples
- Similarity of each match
- Retrieved question
- Retrieved answer
- Relevant state/rule differences
- Same-template and same-group indicators

For structured states, display a readable compact representation.

Do not print enormous raw JSON objects when a concise structured rendering is sufficient.

However, preserve enough information for a human to judge whether the retrieved exemplar actually requires similar reasoning.

Include examples from:

- `choice`
- `noul`
- `score`

Include high-similarity, medium-similarity, and low-similarity cases based on the observed similarity distribution.

Also include:

- Cases with several nearly identical neighbors
- Cases where Top-1 and Top-2 differ substantially
- Cases where the retrieved examples have different ground-truth labels
- Cases dominated by the same template
- Cases where retrieval appears semantically questionable

Selection should be deterministic, with query IDs recorded.

The purpose is to inspect retrieval quality, not just demonstrate successful examples.

## 10. Quantitative diagnostics

Create a summary report:

`results/r0/summary.md`

Report results overall and separately for each kind.

### Retrieval similarity

Calculate:

- Number of evaluated queries
- Mean Top-1 similarity
- Median Top-1 similarity
- Top-1 similarity standard deviation
- Top-1 similarity percentiles: P10, P25, P50, P75, P90
- Mean Top-5 similarity
- Mean Top-1 minus Top-2 similarity gap
- Queries returning fewer than K matches

### Retrieval structure

Calculate:

- Same-group rate at Top-1 and Top-5
- Same-template rate at Top-1 and Top-5
- Same-source-instance rate at Top-1 and Top-5
- Same-scenario-family rate at Top-1 and Top-5
- Different-template retrieval rate
- Unique retrieved exemplar count
- Most frequently retrieved exemplar IDs
- Frequency distribution of retrieved templates

For Top-5 rates, define whether the statistic means any matching neighbor or the fraction of matching neighbors. Prefer reporting both when practical.

### Ground-truth distribution

Report:

- Query ground-truth label distribution
- Top-1 retrieved ground-truth distribution
- Top-5 retrieved ground-truth distribution
- Agreement between query and Top-1 answer indices
- Diversity of retrieved answers within Top-5

These are diagnostics, not accuracy measurements.

Do not treat matching answer indices as proof of semantic correctness.

Different options and score meanings may use the same numerical answer index.

Do not implement kNN voting as part of R0.

### Kind and score filtering

Report:

- Wrong-kind retrieval count
- Score-level mismatch count
- Queries with no eligible candidates

Both mismatch counts must be zero.

## 11. Retrieval quality and template bias

Pay special attention to template-induced similarity.

Open Jev may contain related examples derived from common:

- Scenario families
- Source instances
- Templates
- Counterfactual variants

A high cosine similarity may mean that two examples share boilerplate rather than useful reasoning structure.

Analyze this explicitly.

For example, compare:

1. Same-template Top-1 matches
2. Different-template Top-1 matches
3. Top-1 matches from different scenario families

Do not automatically consider same-template retrieval bad.

Instead determine whether the matches appear genuinely useful for few-shot inference.

Counterfactual variants are especially interesting because they may be nearly identical in text while having different correct answers.

Highlight such cases in the report.

If the validation split is genuinely template-family disjoint from the training split, report that fact as an observed property rather than assuming it from the metadata policy name.

## 12. Similarity distribution

Generate machine-readable histogram data or simple plots for:

- Top-1 cosine similarity by kind
- Top-1 minus Top-2 similarity gap
- Same-template versus different-template similarities
- Score-level groups, where sample sizes permit

Use existing project plotting or reporting utilities if available.

Do not introduce a heavy plotting dependency solely for R0.

CSV histogram data is acceptable.

This information will later help explore similarity thresholds for adaptive retrieval.

**Do not optimize or select a similarity threshold using the test set.**

R0 should characterize the similarity distribution, not declare an optimal gate.

R0 is complete when:

1. The tool compiles in the existing build environment.
2. The existing exemplar database is opened read-only.
3. English validation queries are processed.
4. Query embeddings use the same model configuration as the exemplar database.
5. Kind-specific filtering works correctly.
6. Score-level filtering works correctly.
7. Top-5 nearest exemplars are retrieved.
8. Per-query diagnostics are saved to JSONL.
9. Human-readable retrieval examples are produced.
10. Similarity distributions are summarized.
11. Same-group, same-template, and source-family relationships are analyzed.
12. No validation record is inserted into the exemplar database.
13. Relevant automated tests pass.
14. The final report identifies both strengths and weaknesses of the retrieval results.

## 18. Final report and recommendation

After running R0, provide:

- Changed and added files
- Build instructions
- Actual command used
- Number of validation queries evaluated
- Results by kind
- Similarity distributions
- Representative successful retrievals
- Representative questionable retrievals
- Template and counterfactual bias findings
- Embedding and search latency
- Test execution results
- Limitations and unresolved issues

Finish with one of the following recommendations:

**A. Ready for R1**

Retrieval appears sufficiently relevant and structurally diverse to justify a controlled retrieved 1-shot inference experiment.

**B. Improve canonical embedding text first**

Retrieval is dominated by incidental details, irrelevant candidates, or boilerplate, making the current neighbors questionable for few-shot prompting.

**C. Revise retrieval filters**

The embedding representation appears useful, but retrieval quality is limited by task mixing, score-level differences, template concentration, or candidate selection policies.

Base the recommendation on actual observed retrieval results rather than an arbitrary cosine-similarity threshold.

## Final instruction

R0 is a diagnostic experiment.

Its purpose is not to prove that retrieval improves accuracy.

Its purpose is to establish whether the nearest training exemplars are semantically relevant and plausibly useful as demonstrations.

Keep the implementation small, reproducible, and independent from the existing pjev inference pipeline.

Do not begin R1 until the R0 retrieval results have been inspected and summarized.
