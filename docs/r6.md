# R6 — Model-Specific Calibration Generation

## Objective

Extend the `pjev` release-candidate implementation with a production-supported calibration generation command.

The command must generate a model-specific `calibration.json` using:

- A user-specified GGUF inference model.
- The existing `models/examplar.db` database.
- Ground-truth labels stored in the exemplar database.
- Candidate logits collected from actual model inference.
- The production inference formulations implemented in R5.

R6 is a production feature, not another benchmark experiment.

The primary goal is to allow users to regenerate calibration parameters when changing the inference model.

Do not restore the R1–R4 experimental executables or their analysis infrastructure.

---

## 1. Command-Line Interface

Implement a new production command:

```bash
pjev calibrate \
  --model models/bonsai2_2b.gguf \
  --database models/examplar.db \
  --output models/calibration.json
```

Use the existing CLI architecture and naming conventions.

Supported arguments:

| Argument | Description |
|---|---|
| `--model` | Path to the user-selected GGUF inference model |
| `--database` | Path to the exemplar SQLite database |
| `--output` | Output calibration JSON path |
| `--seed` | Deterministic sampling seed |
| `--max-samples` | Optional maximum number of calibration examples |
| `--validation-ratio` | Fraction reserved for calibration validation |
| `--batch-size` | Processing batch size, where supported |
| `--threads` | CPU thread configuration |
| `--verbose` | Additional progress and diagnostic output |

Default database:

`models/examplar.db`

Default output:

`models/calibration.json`

Use existing runtime defaults for model execution settings unless an explicit override is provided.

Do not silently change context size, candidate scoring, or prompt semantics during calibration.

---

## 2. Database Integration

Read calibration examples directly from the existing exemplar database.

Use SQLite in read-only mode.

Preserve the existing schema.

Do not create additional tables or mutate records.

Reuse existing components for:

- SQLite access
- LZ4 decompression
- Exemplar decoding
- Task-kind identification
- Ground-truth extraction
- Candidate construction
- XXH64 identifiers
- Eligibility validation

Inspect the actual database schema before implementation.

Do not assume that every database row contains a valid calibration example.

### Eligibility rules

Accept examples only when:

- The task kind is supported.
- Input fields are complete and valid.
- Candidate answers are available.
- Exactly one ground-truth answer is identifiable.
- Ground-truth identity maps unambiguously to a candidate.
- The example can be formatted using the production inference implementation.

Reject invalid examples with a recorded reason.

Do not silently replace missing labels with guessed answers.

Report eligible, rejected, and processed example counts by task kind.

---

## 3. Data Partitioning and Leakage Prevention

Calibration must not evaluate a query using its own answer as a retrieved demonstration.

Separate the database into:

1. Demonstration retrieval pool.
2. Calibration-fitting queries.
3. Calibration-validation queries.

Use deterministic partitioning.

Where metadata permits, partition by `group_id` or source family rather than individual rows.

Ensure that queries from the same protected group do not cross partition boundaries.

The retrieval pool must exclude calibration-fitting and validation groups.

If the database contains near-duplicates or related scenario variants, use the existing leakage-prevention mechanisms where available.

Do not invent unavailable source-family metadata.

Document which grouping guarantees were actually enforceable.

### Small datasets

If the available data is insufficient:

- Report the insufficiency.
- Do not silently weaken eligibility rules.
- Do not produce an apparently valid but statistically unsupported calibration.
- Exit with a meaningful error unless an explicitly supported reduced-data mode is available.

Do not reuse validation labels to fit calibration parameters.

---

## 4. Production Formulation Compatibility

Calibration must use the same candidate formulation as the production runtime.

The previous calibration configuration used:

```json
{
  "formulation": {
    "candidate_scheme": "natural",
    "layout": "auto",
    "prior_correction": true
  }
}
```

However, the R4 reference experiments used the `letters` candidate scheme.

Do not assume that calibration parameters are transferable between these formulations.

Inspect the current R5 implementation and use its actual production settings.

Avoid copying formulation metadata from an older calibration file without verifying compatibility.

### Task-specific inference

Use the following configurations:

| Task kind | Calibration inference |
|---|---|
| `choice` | Nearest 2-shot, Order A |
| `noul` | Nearest 1-shot |
| `score` | S1 Zero-shot |

For `choice`, the prompt contains:

1. Second-nearest eligible demonstration.
2. Nearest eligible demonstration.
3. Target query.

For `noul`, the prompt contains the single nearest eligible demonstration.

For `score`, use the original zero-shot inference path.

### Score kNN exclusion

The normal Score inference path uses similarity-weighted kNN-5.

Do not apply LLM temperature scaling or prior-logit correction to kNN similarity votes.

The generated Score calibration parameters are exclusively for the LLM-based zero-shot fallback.

Do not introduce a separate kNN calibration algorithm in R6.

---

## 5. Missing-Exemplar Fallback

Preserve R5's deterministic fallback rules.

Required exemplar counts:

- Choice: 2
- Noul: 1
- Score kNN: 5

When a calibration query cannot retrieve the required demonstrations for Choice or Noul, execute S1 Zero-shot using that task's production fallback path.

Record whether the calibration query used the primary inference path or fallback.

Do not replace missing demonstrations with arbitrary examples.

Do not silently reduce the number of shots.

### Mixed-path calibration

A calibration set may contain both primary-path and fallback-path queries.

Do not assume that the corresponding logits follow identical distributions.

Record inference-path identity for every collected sample.

Fit and report calibration quality separately for primary-path and fallback-path samples.

If a single set of task-level parameters cannot be justified across the different paths, extend the calibration configuration to support path-specific parameters while preserving compatibility with the existing version-1 schema.

Do not silently overwrite an existing parameter's meaning.

---

## 6. Candidate Logit Collection

For each calibration query:

1. Decode the database record.
2. Determine the task kind.
3. Construct the production inference prompt.
4. Retrieve demonstrations where required.
5. Execute the user-selected GGUF model.
6. Extract candidate logits using the production candidate-scoring implementation.
7. Align the ground-truth answer with the candidate index.
8. Record the uncalibrated candidate logits and the correct candidate index.

Do not generate free-form model answers.

Do not use chain-of-thought generation.

Do not use calibration parameters while collecting raw logits.

Calibration fitting must operate on uncalibrated model outputs.

### Reproducibility

Record:

- Model SHA-256
- Database identity or fingerprint
- Calibration seed
- Task kind
- Prompt formulation
- Inference-path identity
- Candidate layout
- Sampling and partition configuration
- Processing status

Use deterministic sampling and stable ordering.

Do not unnecessarily store full task text in calibration outputs.

---

## 7. Calibration Algorithm

Reuse the project's existing temperature-scaling and prior-correction implementation.

Do not independently invent a new calibration formula if one already exists.

The intended calibration family is:

- Temperature scaling
- Task-specific prior correction

Fit parameters using candidate logits and ground-truth candidate indices.

Minimize negative log-likelihood (NLL).

Use numerically stable softmax and log-sum-exp calculations.

### Parameters

Support:

- `choice_temperature`
- `choice_prior_alpha`
- `noul_temperature`
- `noul_prior_alpha`
- `score_temperature`
- `score_prior_alpha`

Preserve the exact semantic interpretation of the existing parameters.

Do not assume that prior-alpha is a simple class-frequency exponent without checking the current implementation.

### Optimization

Requirements:

- Temperature must be finite and strictly positive.
- Prior-alpha must remain within the bounds supported by the existing implementation.
- Optimization must be deterministic.
- Handle non-finite logits safely.
- Detect degenerate label distributions.
- Reject invalid optimization results.
- Report boundary solutions explicitly.

Do not choose parameters based on classification accuracy alone.

Temperature calibration primarily optimizes probability quality, not necessarily accuracy.

---

## 8. Calibration Quality Evaluation

Evaluate both uncalibrated and calibrated outputs on the separate calibration-validation partition.

Report by task kind and inference path:

- Sample count
- Accuracy
- NLL
- Brier score
- Expected Calibration Error (ECE)
- Mean maximum predicted probability
- Mean confidence on correct predictions
- Mean confidence on incorrect predictions

Calculate accuracy from the exact candidate index.

Do not infer correctness from string formatting.

Report changes in:

- Accuracy
- NLL
- Brier score
- ECE

Do not describe lower temperature or reduced confidence alone as better calibration.

A calibration is successful when probability quality improves on validation data without introducing unacceptable regressions.

Include reliability diagnostics where sample counts are sufficient.

### Model comparison

Calibration is model-specific.

Never reuse calibration parameters from a different model without an explicit compatibility check.

---

## 9. Output Format

Generate a JSON file compatible with the existing production calibration loader.

Preserve the current top-level structure wherever possible:

```json
{
  "version": 1,
  "formulation": {
    "candidate_scheme": "letters",
    "layout": "auto",
    "prior_correction": true
  },
  "method": "temperature",
  "model": "<model-identity>",
  "parameters": {
    "choice_prior_alpha": 0.0,
    "choice_temperature": 1.0,
    "noul_prior_alpha": 0.0,
    "noul_temperature": 1.0,
    "score_prior_alpha": 0.0,
    "score_temperature": 1.0
  }
}
```

The numerical values above are placeholders, not recommended calibration results.

Use actual fitted parameters.

The formulation fields must match the active production implementation.

### Schema compatibility

If additional metadata or path-specific calibration is required:

- Introduce a documented schema version.
- Preserve loading of existing version-1 calibration files.
- Update the production loader and generator together.
- Validate model and formulation compatibility at load time.
- Do not silently interpret new parameters using old semantics.

Prefer storing reproducibility and validation details in a companion report rather than unnecessarily expanding the runtime JSON.

---

## 10. Safe Output Handling

Do not overwrite an existing calibration file until the new configuration has passed validation.

Use atomic output replacement:

1. Generate calibration in memory.
2. Validate all fitted parameters.
3. Serialize to a temporary file in the destination directory.
4. Parse the serialized file using the production calibration loader.
5. Verify its compatibility with the specified model and formulation.
6. Atomically replace the destination file.

If generation fails, preserve the existing calibration file.

Report errors clearly.

Do not leave a partially written `calibration.json`.

---

## 11. Production Calibration Loading

Preserve R5's default calibration path:

`models/calibration.json`

The inference runtime must:

- Load calibration during initialization.
- Validate the schema.
- Verify candidate-formulation compatibility.
- Verify model identity when available.
- Apply calibration only to compatible LLM candidate logits.
- Leave Score kNN-5 voting unchanged.
- Apply Score calibration to zero-shot fallback logits.

Do not load or parse the JSON for every inference request.

Do not silently apply incompatible calibration parameters.

The `calibrate` command must not require an existing calibration file to function.

---

## 12. Performance and Resource Usage

Calibration may require many LLM evaluations.

Avoid unnecessary memory usage.

Load the inference model once.

Load the embedding model once when retrieval is required.

Open the database using the existing read-only infrastructure.

Reuse allocated contexts and buffers where safe.

Process examples incrementally.

Do not keep full prompts, decoded records, or unnecessary embeddings in memory after their logits have been collected.

Display progress including:

- Processed examples
- Accepted examples
- Rejected examples
- Progress by task kind
- Current processing stage

Avoid excessive per-example logging by default.

## Acceptance Criteria

R6 is complete when:

- Users can specify a GGUF model and generate its calibration configuration from `examplar.db`.
- Calibration uses ground-truth-labelled examples.
- Calibration samples are separated from their retrieval demonstration pool.
- Candidate logits use the actual production inference formulation.
- Generated parameters are deterministic for identical inputs and settings.
- The generated JSON is compatible with the production loader.
- Existing calibration files are protected from failed generation.
- Normal inference loads the generated calibration automatically.
- Score kNN-5 is not incorrectly modified by LLM calibration.
- Zero-shot fallback uses compatible calibration.
- Existing task-aware routing remains unchanged.
- All relevant production tests pass.

The final implementation must be maintainable, reproducible, and independent of the removed R1–R4 experimental executables.
