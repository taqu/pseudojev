## Selected routing policy

Frozen R4 policy `B_task_only@A_latency` (`frozen_policy.json` sha256 `22556532…c327`):

| Task kind | Strategy | Parameters |
|---|---|---|
| `choice` | Nearest 2-shot, order A | demonstrations: second-nearest, nearest, then the query; candidate-logit argmax |
| `noul` | Nearest 1-shot | R1 prompt (`r1-demo-turn-v1`), candidate-logit argmax |
| `score` | Similarity-weighted kNN-5 | k = 5, τ = 0.005, w = exp((s − s_max)/τ), s = cos(π·hamming/768); tie → best-ranked neighbour's label; same level count; no inference model |

Decision configuration (as in R1–R4): letter candidates, automatic layout, single candidate order, no
calibration, no prior correction, n_ctx 4096. Neighbour list (R4): rank 1 = R1's top-1 search result;
ranks 2.. = top-10 search in (distance, rowid) order, skipping repeated IDs, exemplars whose content
equals the query and content duplicates. Only fallback: choice → nearest 1-shot when fewer than two
neighbours exist or the 2-shot prompt exceeds the context (validated in R4).

R4 held-out reference (n = 5,811): accuracy 56.75% (choice 45.13%, noul 90.62%, score 35.79%),
composed mean latency 495.0 ms. These are regression references, not production guarantees.

## What changed

- **One production entry point**: `DecisionService`, implemented by `TaskRouter` (`src/routing`), used
  by CLI `--direct`, the background worker and the HTTP server. One `switch` on the task kind.
- **Shared infrastructure**: `RouterRuntime` owns model / database lifecycle (loaded once per process,
  in R4's order); `ExemplarStore` (`src/retrieval`) provides read-only SQLite access, LZ4 payloads,
  allowlist filtering and the R1 search loop; `task_mapping` holds candidate mapping, demonstration
  construction and the content key; `knn` holds similarity, label mapping and voting.
- **Interfaces** (additive): optional `domain` / `family` per API question and `--domain` / `--family`
  on the CLI (retrieval context, as in R4's embedding text); a JSON-object state is embedded field by
  field; new error code `no_eligible_exemplar` (HTTP 422); `/version` reports `routing_policy`;
  resource flags `--embedding-model`, `--exemplar-db`, `--exemplar-allowlist` and matching
  `pjev.json` keys. Worker IPC protocol v2 (versioned endpoint name).
- **Deprecated, accepted with a warning**: `--calibration`, `--ensemble`, `--layout`, `--scheme`,
  `--no-kv-reuse`, `--no-batch-questions`, `--questions` (the decision configuration is fixed by the
  policy).
- **Build**: `pjev-core` (no llama.cpp) and `pjev-runtime` libraries; `PJEV_BUILD_TOOLS` and
  `BUILD_TESTING` options; tests link the libraries.

## Performance smoke test

Conditions: Windows 11, 24-core / 32-thread CPU, RTX 4060 Ti (embedding model on Vulkan), inference on
CPU with 12 threads. **The machine was shared with unrelated asset-build processes** (shader / texture
conversion, 15–97% total CPU during the session), so absolute numbers are inflated; comparisons below
are made under identical conditions.

Same 60 held-out queries (the first 60 of the R4 evaluation partition), one warm-up pass, end-to-end
decision time:

| Kind | n | Release candidate | R4 binary, same session | R4 binary, 2026-10-20 (idle) |
|---|---:|---:|---:|---:|
| choice | 30 | 1632.7 ms | 1489.9 ms | 807.4 ms |
| noul | 15 | 1076.9 ms | 1073.0 ms | 590.7 ms |
| score | 15 | 187.0 ms | 100.6 ms | 87.1 ms |
| all | 60 | 1132.3 ms | 1038.3 ms | 573.2 ms |

- noul (identical plan) matches R4's binary within 0.4%.
- choice (+143 ms) and score (+86 ms) pay one extra search: the release runs R1's top-1 search **and**
  the top-10 search, because R4's recorded predictions use rank 1 from the top-1 search (the two
  searches rank a different exemplar first on 96 of 5,811 held-out queries, typically among exact
  Hamming ties). R4's live plan and its cost model used the top-10 search alone.
- Composed from R4's own per-stage measurements over all 5,811 held-out queries, the release plan
  costs **593.2 ms** mean (choice 683.2, noul 518.1, score 217.3) versus the 495.0 ms R4 reported for
  B. This is above policy A's 519.9 ms — see Known limitations.
- Second sample (20 random held-out queries per kind, seed 20261021): score 231.7 ms vs 223.0 ms
  composed from R4 stages for the same plan (+4%).

No regression beyond the extra search was found. These are smoke measurements on 60–72 decisions,
not a benchmark; they do not establish equivalence with R4's latency figures.

## Known limitations and open decisions

1. **Latency vs exact parity (decision needed).** Exact reproduction of R4's predictions requires the
   extra top-1 search (+~98 ms mean, composed). Dropping it (top-10 search only, R4's live plan)
   restores ~495 ms but changes the neighbour list on ~1.4% of choice / score queries (82 of 4,212
   held-out queries) and would fail the golden cases tagged `topk_rank1_differs_from_r1`. The release
   keeps exact parity.
2. The decision engine still contains code no production entry point reaches (ensembles, batch KV
   reuse, prior correction, calibration temperature, natural-label scheme). It was left unchanged to
   avoid touching the validated core in a release candidate; its unit tests still pass.
3. `score` works only for level counts present in the bank (3, 4, 5); others return
   `no_eligible_exemplar`. English only validated.
4. The first decision after start-up can be much slower (cold caches; one run took 42 s on this
   machine); the worker amortizes it.
5. Only Windows x86_64 was built and tested; Linux / macOS CI runs were not triggered (branch not
   pushed). The release workflow cannot publish `-rc` tags as written (it requires VERSION to equal
   the tag and the binary version to be X.Y.Z).
6. On Windows, build directories under `%TEMP%` fail (llama.cpp's Vulkan shader generator); the
   SQLite database directory must be writable (WAL side files).

## Release packaging

`cpack -C Release` → `pjev-0.9.0-windows-x86_64.zip` (21 MB) containing only `pjev.exe`, `pjev.json`
(all four resource keys), `README.md`, `LICENSE`, `THIRD-PARTY-NOTICES.md`. (Before this release the
archive also carried llama.cpp's headers, static libraries and CMake files; now only the `runtime`
install component is packaged.)

Not included: models, exemplar database, allowlist, datasets, experimental executables, reports,
logs. The model / data licenses (Apache-2.0 models; CC0 1.0 / CC BY 4.0 Open-Jev data with some
source text whose license is unverified; MIT OpenJevData-140k) were not judged sufficient to bundle
them; README "Runtime resources" documents how to obtain and place them.

`scripts/smoke-test.sh` on the unpacked archive: passes without resources (reports them missing) and,
with the four resources placed next to the executable, loads them via `pjev.json` and answers one
noul, choice and score decision. No tag was created and nothing was pushed.
