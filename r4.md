# R4 — Nearest 2-shot, kNN Classification, and Task-Aware Routing

## Objective

Implement and evaluate R4 for the `pjev` project, extending the existing R1, R2, and R3 experiments.

R3 established that nearest-neighbour exemplar selection improves overall accuracy over random 1-shot selection, but the benefit varies substantially by task type.

R4 must answer three questions:

1. **Does Nearest 2-shot provide a meaningful accuracy improvement over Nearest 1-shot, sufficient to justify additional inference tokens?**
2. **Can a simple embedding-based kNN classifier reproduce the strong Nearest 1-shot performance on `noul`, without running the inference LLM?**
3. **Can task-aware routing reduce average latency while preserving most or all of the accuracy of the best available strategy?**

The goal is not to maximize benchmark accuracy at any cost.

The goal is to identify a reliable, reproducible, and computationally efficient inference policy suitable for eventual integration into `pjev`.

Do not modify the production inference defaults during R4.

## 3. R4-A — Nearest 2-shot

### 3.1 Retrieval

Retrieve the two nearest eligible exemplars using the existing R1 retrieval mechanism.

Preserve:

- Training allowlist restrictions
- One-hot answer eligibility
- Task kind matching
- Score level-count matching
- Query self-exclusion
- Existing leakage checks

Both exemplars must be distinct.

Use deterministic retrieval ordering and tie-breaking.

Do not introduce a new embedding model, reranker, or vector index.

### 3.2 Prompt construction

Preserve the existing `r1-demo-turn-v1` format.

Represent each demonstration as:

1. S1-style user turn containing the exemplar task.
2. Assistant turn containing the exemplar answer label.

Append the unchanged S1 query prompt after the demonstrations.

Keep the existing candidate-letter mapping and candidate-logit scoring.

Do not introduce chain-of-thought generation, free-form answers, or additional instructions.

### 3.3 Demonstration ordering

Compare two deterministic orders:

**Order A:**

1. Second-nearest exemplar
2. Nearest exemplar
3. Target query

**Order B:**

1. Nearest exemplar
2. Second-nearest exemplar
3. Target query

This isolates demonstration-order effects.

Select the preferred order using only the tuning partition.

Do not select the best order separately for each held-out query.

### 3.4 Required comparisons

Evaluate:

- S1 Zero-shot
- R1 Nearest 1-shot
- R4 Nearest 2-shot, Order A
- R4 Nearest 2-shot, Order B

Report the accuracy difference between Nearest 2-shot and Nearest 1-shot.

Also report additional prompt tokens and measured inference latency.

A small accuracy improvement that requires substantially more computation should not automatically be considered a successful result.

### 3.5 Context handling

Keep R1's existing no-truncation policy.

Do not silently truncate demonstrations or target queries.

If the prompt exceeds the available context, record a structured failure.

Report context-limit failures separately by task kind and strategy.

Any fallback policy must be defined before final evaluation and applied consistently.

## 4. R4-B — Embedding kNN Classification

R3 showed that the Nearest 1-shot advantage is concentrated in `noul`.

In particular:

- Nearest 1-shot `noul` accuracy: 90.62%
- Random 1-shot `noul` accuracy: 79.01%
- Zero-shot `noul` accuracy: 63.41%
- Nearest demonstration label matches the ground truth in 83.49% of cases.
- The R1 model predicts the nearest demonstration label in 89.99% of cases.

This suggests that part of the improvement may result from label transfer rather than generalization from the demonstration.

R4 must test this explicitly.

### 4.1 kNN-1 baseline

Implement a deterministic nearest-neighbour classifier.

For each query:

1. Compute the query embedding using the existing embedding model.
2. Retrieve the nearest eligible training exemplar.
3. Extract the exemplar's ground-truth semantic answer.
4. Map that answer to the query's corresponding candidate.
5. Return the mapped candidate without invoking the inference LLM.

Use the same retrieval pool and eligibility rules as R1.

Never compare answer letters as if their semantics were universally identical.

For tasks where answer labels depend on candidate ordering, translate through the actual semantic answer identity.

If no valid mapping exists, record an explicit failure or abstention.

Do not infer a mapping from the query's ground-truth answer.

### 4.2 kNN-K baseline

Evaluate:

- k = 1
- k = 3
- k = 5

For k greater than 1, support:

**Uniform voting**

Each eligible neighbour contributes one vote.

**Similarity-weighted voting**

Weight neighbours using their retrieval similarity.

The weighting formula must be deterministic, documented, and numerically stable.

Any temperature or weighting hyperparameter must be selected on the tuning partition.

Define deterministic tie-breaking.

Do not use the target query's ground-truth label for any decision.

### 4.3 Task support

Prioritize `noul`.

Evaluate `score` where semantic label mapping is unambiguous and the number of levels matches.

For `choice`, only enable kNN classification if a meaningful candidate-identity mapping exists independently of the ground truth.

Otherwise report `choice` as unsupported for direct kNN classification.

Do not pretend that the same candidate letter represents the same semantic answer across arbitrary choice queries.

### 4.4 Required diagnostics

Report:

- kNN-1 accuracy
- kNN-3 accuracy
- kNN-5 accuracy
- Uniform vs weighted voting
- Agreement with R1 predictions
- Agreement with R1 demonstration labels
- Neighbour-label consistency
- Mean nearest similarity
- Accuracy by similarity range
- Rescue/harm relative to S1
- Cases where kNN succeeds but R1 fails
- Cases where R1 succeeds but kNN fails

Measure the complete kNN execution latency, including embedding, retrieval, mapping, and voting.

The central question is whether kNN classification approaches or exceeds the accuracy of R1 on `noul` at substantially lower computational cost.

Do not assume that a high exemplar-label agreement rate guarantees equally high kNN accuracy.

## 5. R4-C — Task-Aware Routing

Implement an offline routing evaluator using predictions and measurements from the preceding experiments.

Routing must not use ground-truth labels at inference time.

### 5.1 Candidate actions

Support the following actions:

- `zero_shot`
- `random_1shot`
- `nearest_1shot`
- `nearest_2shot`
- `knn_1`
- `knn_3`
- `knn_5`

Each action must have clearly defined applicability, failure handling, and computational cost.

### 5.2 Routing policies

Evaluate at least three routing approaches.

**Policy A — Static baseline**

Always use R1 Nearest 1-shot.

This is the main reference policy.

**Policy B — Task-only routing**

Choose one action per task kind:

- `choice`
- `noul`
- `score`

Determine the selected action using the tuning partition only.

Do not hardcode the final choices based on the already observed held-out R3 results.

**Policy C — Task-aware adaptive routing**

Allow additional routing based on deterministic features such as:

- Task kind
- Nearest-neighbour similarity
- Neighbour-label agreement
- S1 candidate-logit margin

Investigate whether an adaptive policy improves the accuracy/latency trade-off.

Keep the first implementation simple.

Avoid training a separate complex routing model unless simpler rules demonstrably fail.

### 5.3 Conditional inference cost

Account for the true execution order.

For example, a policy that first computes S1 and then invokes Nearest 1-shot must pay for both LLM evaluations.

Likewise, a policy using retrieval similarity before deciding whether to run S1 must include the retrieval cost.

Do not report the latency of a selected action alone if additional computations were required to select it.

Do not use offline oracle selection based on correctness as a deployable routing strategy.

### 5.4 Policy optimization

Construct an accuracy-versus-latency Pareto frontier on the tuning partition.

Identify policies that are not dominated in both accuracy and latency.

Report candidate policies across several latency budgets rather than optimizing a single arbitrarily chosen threshold.

Include:

- Accuracy
- Mean latency
- P50 latency
- P95 latency
- Mean LLM evaluations per query
- Mean embedding evaluations per query
- Mean prompt tokens
- Routing frequency by task
- Failure rate

Choose a small set of final candidate policies before held-out evaluation.

Do not modify policies after inspecting the final evaluation results.

Use paired comparisons wherever possible.

- Overall accuracy
- Accuracy by task kind

- 95% cluster-bootstrap confidence intervals
- Rescue count
- Harm count

- Error count and exclusion count

### Required pairwise comparisons

1. Nearest 2-shot vs Nearest 1-shot
2. Nearest 2-shot vs Zero-shot
3. kNN-1 vs Nearest 1-shot
4. kNN-3 vs kNN-1
5. kNN-5 vs kNN-1
6. Task-only routing vs Nearest 1-shot
7. Adaptive routing vs Nearest 1-shot

Separate confirmatory comparisons from exploratory analyses.

Report confidence intervals even when the result is negative or inconclusive.

## 8. Latency Measurement

Measure real per-query latency rather than estimating it from token counts.

Use the same local hardware and inference backend as R3.

Preserve the existing measurement methodology where possible:

- Load models once.
- Perform untimed warm-up.
- Use consistent execution conditions.
- Record individual query timings.
- Avoid silently excluding failed or slow queries.

Break down latency into:

- Embedding inference
- Nearest-neighbour search
- Database row fetch
- LZ4 decompression
- Prompt construction
- LLM inference
- Candidate scoring
- Total execution time

Report mean, median, P95, and P99 latency.

Clearly distinguish cached or reused intermediate results in offline evaluation from the actual work required by a deployable runtime.

For routing policies, use an explicitly defined end-to-end execution plan to avoid undercounting duplicated computation.

Use a same-session timing comparison for the main finalist strategies where practical.

Do not extrapolate these local measurements into online production latency claims.

## 13. Success Criteria

R4 is successful if it produces reliable evidence about the following:

**Nearest 2-shot**

Does adding a second retrieved example produce a measurable improvement over Nearest 1-shot?

**kNN classification**

Can nearest-neighbour label transfer reproduce the strong `noul` accuracy while eliminating the inference-model execution cost?

**Task-aware routing**

Can a simpler per-task policy reduce latency without sacrificing a meaningful amount of overall accuracy?

**Adaptive routing**

Do dynamic features provide a meaningful benefit beyond simple task-only routing?

A negative result is acceptable and valuable.

Do not force an improvement through additional held-out tuning.

The final deliverable is a reproducible evaluation and a defensible deployment recommendation, not a predetermined accuracy gain.
