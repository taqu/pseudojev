# Task: Implement and Freeze S0 — Digit-Based Baseline for `score`

## Objective

Implement and evaluate a clean baseline for the `score` primitive using digit candidate tokens:

```text
0
1
2
3
...
```

The purpose of S0 is not to optimize `score` yet.

The purpose is to establish a reproducible reference configuration against which later experiments such as:

```text
S1: letter labels
S2: letter-label rotation ensemble
```

can be compared.

S0 should preserve the natural ordinal interpretation:

```text
0 < 1 < 2 < 3 < ...
```

and use one candidate digit token per score level.

Do not add rotation, few-shot examples, or other experimental changes in this task.

---

# Core design

For a `score` task with `N` ordinal levels:

```text
semantic level 0 -> candidate token "0"
semantic level 1 -> candidate token "1"
semantic level 2 -> candidate token "2"
...
semantic level N-1 -> candidate token "<N-1>"
```

The semantic level and digit label are intentionally aligned in S0.

This is the baseline formulation.

---

# Prompt format

Use an ordinal prompt that makes score ordering explicit.

Conceptually:

```text
State:
{state}

Question:
{question}

Possible answers (ordered from lowest to highest):
0: {level 0 description}
1: {level 1 description}
2: {level 2 description}
3: {level 3 description}

Answer:
```

The exact wording should follow the existing PromptStrategy conventions unless there is a strong reason to change it.

Do not change unrelated prompt layout in this experiment.

The important invariant is:

```text
display order == semantic score order
```

and:

```text
digit label == semantic score level
```

---

# Do not rotate score levels

Do not apply E2-style semantic rotation.

This would break the ordinal structure.

For example, do not create mappings such as:

```text
0 -> semantic level 2
1 -> semantic level 3
2 -> semantic level 0
3 -> semantic level 1
```

in S0.

The score ordering must remain stable and monotonic.

For example:


Each candidate must tokenize to exactly one token.

If a required digit is not a single token:

- report the offending candidate;
- do not silently substitute another representation.

Record the token IDs used by S0.

# Expected score

Compute expected score using semantic levels:

```text
expected_score =
    sum_i i * P(level_i)
```

For S0, this is numerically aligned with the digit candidate labels.

Keep this implementation semantic rather than parsing candidate text back into integers where possible.

---

# Primary prediction

The categorical prediction remains:

```text
argmax_i P(level_i)
```

Report both:

```text
predicted discrete level
expected continuous score
```

These are different outputs and both are useful.

# Discrete MAE

For labeled sample with:

```text
ground_truth = y
predicted_level = y_hat
```

compute:

```text
absolute_error =
    abs(y_hat - y)
```

and:

```text
MAE =
    mean(absolute_error)
```

Lower is better.

This distinguishes:

```text
off by 1
```

from:

```text
off by 3
```

which accuracy cannot.

---

# Expected-score MAE

Also compute:

```text
expected_score_error =
    abs(expected_score - ground_truth_level)
```

and report:

```text
expected_score_MAE
```

This is important because the probability distribution may improve even when argmax does not change.

Example:

```text
ground truth = 3

baseline probabilities:
0.10 0.20 0.40 0.30

improved probabilities:
0.02 0.08 0.30 0.60
```

Both might differ in discrete behavior depending on the case, but expected-score error captures distribution movement toward the correct ordinal target.

---

# NLL

For each labeled example:

```text
NLL_i =
    -log(P(ground_truth_level))
```

Aggregate by mean.

Use numerically safe probability clamping.

---

# Multiclass Brier score

For `K` score levels:

```text
Brier_i =
    sum_j (P_j - Y_j)^2
```

where `Y` is the one-hot ground-truth vector.

Use the same convention already used by the benchmark suite.

If normalized by `K`, document it clearly and use the same convention in S1/S2 later.

---

# ECE

Use the benchmark's existing ECE implementation.

Confidence should be:

```text
max probability
```

and correctness should be based on discrete argmax prediction.

Do not introduce a different ECE definition specifically for S0.

---

# QWK

If practical, compute Quadratic Weighted Kappa.

This is especially useful for ordinal score tasks because it penalizes larger disagreements more heavily.

Use the standard quadratic weighting based on distance between score levels.

If QWK is not already implemented and adding it would significantly complicate this task, it may be added in a small isolated metrics component.

Do not block the whole S0 implementation solely on QWK if all other metrics are available.

---

# Signed ordinal margin

Add an ordinal-confidence diagnostic.

For each labeled sample, define:

```text
L_gt =
    logit of ground-truth level

L_best_wrong =
    maximum logit among all incorrect levels

signed_margin =
    L_gt - L_best_wrong
```

Interpretation:

```text
signed_margin > 0
    correct class has highest score

signed_margin < 0
    some wrong class outranks the correct class

larger positive value
    stronger classification
```

Report:

```text
mean signed margin
median signed margin
p10 signed margin
minimum signed margin
```

This makes saturated-accuracy splits easier to compare.

---

# Ordering consistency

At minimum report cases where:

```text

```

or where probability mass is highly non-local around the predicted / true level.

A simple initial metric can be:

```text

    abs(expected_score - predicted_level)
```

Report the mean.

If an existing ordering-consistency metric already exists, use it instead.

Do not invent a complicated new metric unless necessary.
